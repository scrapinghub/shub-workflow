# Architecture diagrams for shub-workflow projects

Two kinds, one visual family:

| Kind | What it shows | How it is laid out |
| --- | --- | --- |
| **Pipeline / workflow** | the stages of a workflow as banded containers — jobs inside, a Role box per band, storages between them | **by you**, on a grid; Graphviz only routes the edges |
| **Class hierarchy** | the project's script classes as UML boxes, base above subclass | **by Graphviz** (`dot`) — a tree is what it is good at |

Both are **generated from an editable model, never hand-drawn**: the diagram is code, lives next to
the project, and is re-rendered when the architecture changes. Do not introduce a `.drawio` (or any
other binary editor source) — a diagram nobody can diff is a diagram that goes stale.

## Before you draw anything

A diagram asserts how the system works, so get the architecture from the project itself, in this
order: its knowledge-base skill if it has one, then its README, then the code. Read the scheduler
and the crawl managers to learn **how many jobs of each component actually run** — that is the
detail diagrams get wrong most often (one script can be scheduled as one rotating job, or as one job
per source).

When what you are asked to draw disagrees with the code — a component that is configured but
disabled, a box per source where the code schedules one shared job — **draw what was asked and say
so in one line.** The asker usually knows something the code does not show; silently "correcting"
them produces a diagram neither of you trusts.

## Procedure

1. **Set the folder up.** Copy [examples/diagram_engine.py](examples/diagram_engine.py) verbatim
   into `<project>/diagrams/`. Never edit it — picking up a fix later must stay a re-copy.
2. **Write the model** in `<project>/diagrams/workflow_gen.py`, starting from
   [examples/workflow_gen.py](examples/workflow_gen.py). It is plain data: stages, the cells in
   each, the edges between them. Vocabulary: [references/model-reference.md](references/model-reference.md).
   For a class diagram, copy [examples/class_hierarchy_gen.py](examples/class_hierarchy_gen.py)
   instead — it is self-contained and needs no engine.
3. **Render**: `python3 diagrams/workflow_gen.py`. It writes the `.dot` beside the generator and the
   PNG where the README references it.
4. **Look at the PNG.** This is not optional and not a formality: the model renders happily into
   something unreadable — labels on top of arrows, arrows entering the wrong side of a box, dots
   hidden behind an edge. Every one of those is invisible in the model and obvious in the image.
   Iterate: render, look, adjust, render again.
5. Reference the PNG from the README, and say there that it is generated by the model so the next
   person edits the right file.

## The house style

Set by `diagram_engine.py`; change it there only if the whole family should change.

- **One warm palette**: cream page, amber fill, terracotta stroke, dark indigo text and edges. Fill
  means "a thing that runs or stores"; the page colour means "a container".
- **Bands**: each pipeline stage is a framed band with its title at the top-left and a bulleted
  **Role box** at the far end saying what that stage does. Role bullets start with a capital; edge
  labels are lowercase.
- **Flow left to right** (`ORIENTATION = "horizontal"`). Vertical still works and is a one-word
  change, but every project here is laid out horizontally.
- **Repetition is a stack, not a crowd**: N identical jobs are one box with a "⋮" under it, or a few
  boxes and a "⋮". Draw a box per instance only when the edges differ per instance.
- **Edge weight carries meaning** — `thin` (control / naming), `thick` (ordinary data flow),
  `dashed` (fan-out), `bus` (one wide arrow standing for a whole band's traffic), `trunk` (wider
  still: where the bulk of the bytes go).
- An arrow about a **stage as a whole** lands on that band's border, not on one job inside it.

## Critical rules

- **Never hand-edit the `.dot` or the PNG.** Both are build products; the next render discards the
  edit. If the shape is wrong, the model is wrong.
- **Positions are yours, Graphviz's are not.** Pipeline diagrams carry an explicit `pos` per node
  and render with `neato -n2` for exactly this reason — left to its own ranking, Graphviz reorders
  bands and columns between runs for no visible reason. Do not "simplify" that away.
- **Two render passes are load-bearing.** HTML-table nodes size themselves, so the engine lays out,
  asks Graphviz what it actually drew, and lays out again. Without it every gap is a guess and the
  stacks overflow their lanes.
- **Edge routing has sharp edges** — ports silently ignored, a crash from an endpoint on a node's
  border, corners flipping to the wrong side. All of them, and the fix for each, are in
  [references/graphviz-traps.md](references/graphviz-traps.md). Read it before fighting a stubborn
  arrow.

## Requirements

Graphviz (`neato` and `dot`) on PATH. Nothing else — the engine is one file of standard library
Python, and the diagrams are a documentation tool, not part of the project's runtime dependencies.
